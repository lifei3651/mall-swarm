# 商城非真机功能收口：支付、发货、退款、库存与资金

日期：2026-09-25（Asia/Shanghai）。基线为线上 1.0.167；本次检查和修改本地源码，另做正式环境聚合只读复核。没有封包、留档、部署、上传微信或写入正式订单/资金。

## 本次实际检查

按 P0-05 的订单—发货—退款—资金交界，检查了后台取消入口、服务层、发货服务和客户异常退款入口。发货服务先锁订单行；客户异常退款在锁内识别已开始发货；旧售后免寄回退款同时核对主状态、旧运单字段和包裹记录。后台取消待付款走订单锁并只允许状态 0。

发现并修正后台“取消待发货”独有的三个缺口：

1. 原先用未加锁的订单状态判断是否可取消，和并发发货存在旧状态竞态。现在与发货共用订单行锁，锁内重查状态。
2. 多件订单部分发货后主状态仍可能是“待发货”。现在只要旧运单字段或包裹记录表明已开始发货，就拒绝按“未发货整单取消”处理，避免虚假整单退款/库存回补。
3. 实付额包含运费，原后台整单取消复用了“只退商品款”的人工退款路径。现在仅对完全未发货的整单取消补退尚未退还的运费；普通后台人工部分退款不受影响。

## 第二轮：退款与资金归集并发顺序

继续检查退款完成后的资金冲回与定时归集结算，发现同一订单存在相反的数据库行锁顺序：退款链路先锁订单、再锁归集记录；结算任务原先先锁归集记录、再锁订单。两者在售后期边界并发时**可能**互相等待并触发数据库死锁；这是源码风险，未取得正式环境死锁事件证据。

- 将结算改为先按当前租户读取归集记录所属订单号，再锁订单、锁归集记录；锁后重新校验归集记录的订单、租户、状态和金额。
- 补建归集凭证及退款冲回入口也先锁订单，再读取或锁定归集记录，统一同一资金路径的锁序。
- 新增四项锁序/租户/空记录回归；现有归集与退款集成用例继续通过。后端及 common 全量 **815/815**、失败 0、错误 0；未因纯后端改动重跑前端用例。初次定向测试中一项模拟“查不到记录”的桩返回了 Mockito 默认 0 而非数据库的空值，修正测试桩后定向及全量重跑通过。

此轮仍只完成源码与本地测试，没有并发压测 MySQL、正式库死锁日志核对、服务器/微信更新或真实退款。P0-05、FIN-05 的真实订单与账本验收继续开放；当前修复不属于已留档或部署的 1.0.167 精确包。

## 第三轮：全额退款订单关闭与通用功能回归

全额退款的两条完成路径（外部渠道成功后的本地恢复、余额/本地退款）原先都没有检查“关闭订单”数据库更新的影响行数。若因旧状态或租户边界导致更新为 0，退款账务与库存可能提交成功，订单却保留原状态。现在两处均要求更新恰好 1 行，否则抛错回滚同一**本地**事务；外部渠道已成功的售后仍保留可用原售后号恢复的处理状态，不能误报渠道退款失败。补充两条失败回归，并检查同类订单 `ship/cancel/confirmReceive/closePending` 更新调用；这些调用已有影响行数判断。

日常功能回归原入口固定在历史候选 1.0.158（1.0.167 也有独立冻结脚本），当前开发源码无法直接使用，容易混淆“身份门禁拒绝”和“测试失败”。新增 `scripts/run-mall-functional-regression.sh` 作为不绑定固定候选身份的四端全量测试/构建入口；检查当前源码版本一致、迁移计划、敏感文件名、发布合同和语法，但**不**替代冻结包所需的干净提交、上游同步、版本/构建号、迁移哈希、正式主机准入与留档验签。新增三项入口合同回归，包括只读预检及拒绝未知参数。旧 1.0.158/1.0.165/1.0.167 冻结脚本保持不变。

## 第四轮：重复运单的件数核对

继续检查手工、ERP 和表格批量发货的共同幂等边界，发现原服务仅用订单、物流商和运单号判断重复：同一运单首次录入 1 件、重试时填 2 件，也会返回成功或“重复跳过”，使错误件数没有被显式发现。表格内两行相同运单而件数不同也被静默跳过。

- 已存包裹记录优先按订单和运单查询；显式提交件数不等于原记录时拒绝，件数相同仍安全幂等。只有主订单运单字段、没有包裹数量快照的历史记录，在显式件数与当前整单可发数不一致时拒绝并要求人工核对，避免猜测历史数量。
- 批量表格同号同件数只发一次；同号不同件数计为该行错误，不阻断其他正确行，也不把错误行记入“重复跳过”。
- 补 7 项回归，覆盖手工、ERP、已存包裹、同一表格重复行和旧主表运单字段。通用四端功能回归完整通过：后端/common **824/824**、管理后台 **219/219**、小程序 **529/529**、H5 **183/183**、脚本合同 **36/36**；后端与后台生产构建、小程序工程检查及 H5 三种构建通过。没有执行正式物流登记或微信消息投递。

这轮修复也不在已留档、已部署的 1.0.167 精确包中。发货件数和官方轨迹仍须用新候选、真实订单及回执在后续 R 阶段核对；当前不能把本机回归当成正式物流闭环。

## 第五轮：支付渠道与已支付幂等边界

审查微信、支付宝、余额三条支付入口及订单/跨商户交易父单的公共入账方法，发现支付方式选择虽然在部分待支付路径核对，但单商户公共入账可直接覆盖订单原选渠道；已支付幂等分支、余额端点、微信签名回调及支付宝回调/查询的部分路径也未统一核对订单所选渠道。若出现跨渠道重试或渠道结果与本地选择不一致，原代码可能返回“已处理成功”或把待支付订单标记为另一渠道支付。**这是源码发现的风险，未取得正式交易发生该问题的证据。**

- 订单及交易父单在公共入账前先核对已记录支付方式，再处理已支付幂等；不再把不同渠道请求当成同一笔支付的重试。开发环境专用模拟支付仍保持原有入口，正式环境该入口本已禁用。
- 余额端点在待支付及已支付两种状态下都先核对是否选择余额，避免把别的渠道已支付订单报成“余额支付成功”。微信已验签通知、支付宝回调与同步查询在确认订单后先核对选定渠道，不为不匹配的渠道入账或返回成功确认。
- 新增 8 项反例，覆盖单商户/父单、微信/支付宝回调及查询、余额待支付与已支付；同渠道原有幂等用例继续通过。定向测试首次因新单元测试的 DAO 默认桩把空交易 ID 返回为 0 而失败，修正测试桩后重跑通过；未以失败运行冒充通过。通用四端完整回归最终通过：后端/common **832/832**、后台 **219/219**、小程序 **529/529**、H5 **183/183**、脚本合同 **36/36**，后端/后台生产构建、小程序工程检查和 H5 三种构建均通过。

本轮没有真实微信/支付宝通知、余额扣款、正式库写入或新版本 S/W/R；1.0.167 线上固定包不含该修复。后续真实支付验收须分别记录订单所选渠道、实际渠道回执、订单支付状态、余额流水与资金/奖金结果，不能仅凭自动测试关闭 PAY-02、PAY-04、PAY-05 或 P0-05。

## 第六轮：退款时“未发货”证据与库存/运费

同类检查发现，退款完成后的库存回补原先仅看待发货状态、空发货时间与包裹件数合计 0；旧运单号或包裹记录本身存在而件数合计为 0 时，异常退款可能被误当成完全未发货，增加可售库存。顾客异常退款的运费判断也独立重复了一套较弱的“未发货”条件。**这是源码边界风险，不是已发现正式订单错账。**

- 库存回补仅在待发货、无发货时间、无旧运单号、包裹件数为 0 且无任何包裹记录时，才把非实体退货视作未发货；真正的退货退款仍在实物退回后按原规则回补。
- 顾客申请的物流异常/取消退款共用同一个发货证据判断；存在旧运单号或包裹记录时，不能走未发货取消，也不自动退原发货运费。
- 新增 4 项反例（旧运单号、零件数但有包裹记录，覆盖库存与申请运费/取消）；两组定向测试 **15/15**。修改后完整功能回归：后端/common **836/836**（17 + 819）、后台 **219/219**、小程序 **529/529**、H5 **183/183**、脚本合同 **36/36**；后端/后台生产构建、小程序工程检查、H5 三种构建通过。

2026-09-25 正式库**只读**同类扫描：当前待发货但有旧运单号、当前待发货但有包裹记录、其中包裹件数合计为 0 的订单分别为 **0/0/0**。这仅是当时的数据快照，不能证明历史上没有发生，且没有进行真实退款或库存写入。新修复不在已部署的 1.0.167 固定包中，P0-05 仍开放。
