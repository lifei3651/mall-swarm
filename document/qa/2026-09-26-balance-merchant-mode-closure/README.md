## 基线与证据边界

- 线上服务器及三站仍为 `1.0.167 / c40a0e8cea82b8c5081ba0438dc3ced0db0daf37 / 20260924-closure-1.0.167`，正式库迁移 41/41；本轮未改 `VERSION`。用户所说的基座是测试/验证环境，不是客户正式经营商城。

- 源码迁移集合现为 43 条 `V*.sql`；线上 41 条，新增的优惠券与余额/多商户开关迁移尚未在隔离 MySQL 或正式库执行。H2/模拟支付测试不等于 MySQL 并发、第三方回执或账本运行验收。

## 本地已处理的边界

1. `dms_tenant` 增加“允许新增余额交易”“允许新增多商户经营”两个独立开关。迁移对既有客户默认保持开启；新客户由创建服务明确以余额开启、仅平台自营开局。后台模式保存与旧配置快照恢复保留原值并核验权限，不允许普通资料编辑顺带改开关。
2. 余额关闭只停止新余额报价、下单/支付、转账和后台人工加扣；前端不再提供不可用的支付/划转动作。存量钱包、提现清偿、旧订单原路退款、奖金和流水审计继续存在，不能把“无新余额交易”解释为删除旧余额债务。
3. 多商户关闭拒绝新商户入驻/启用、商户商品重新上架、商户商品新下单；公开商品目录、详情和秒杀入口不再展示旧商户商品，目录缓存键包含模式，避免开关后继续命中旧展示。平台自营商品与普通订单路径保留。旧商户订单的**已存在待付款支付及外部支付回调**、退款、结算和审计不按新销售门禁拦截，以免外部已扣款而本地停在未支付。
4. 商户新单与后台关闭开关共享租户行锁，商品/库存条件更新再次复核；秒杀商户活动还在活动入口和提交前检查，拒绝时不能预占库存。H2 服务边界测试枚举秒杀、复购、优惠券、余额、多商户五个开关的 **32 种组合**，检查公开状态和新交易门禁，并验证全关闭后旧单支付回调可继续；该测试 2/2 通过，**不是** 32 条端到端交易，更不是 MySQL 并发或客户项目组合验收。
5. 同类扫描发现：仅凭前端隐藏支付选项并不能阻止直达接口以未配置的微信/支付宝方式提交，原先可能生成无法支付的待付款订单。后续源码在显式支付方式的运费报价、提交及最终落单处加入服务端通道可用性校验；拒绝新订单时订单数和库存应不变。渠道后来关闭也不能拦截历史订单已核验的支付回调和退款，以免外部已扣款、本地未入账。该项列为 P1-17；新增定向 37 项、补丁后独立全量 Maven 回归均通过。`isConfigured` 只是本地配置完整性判断，不等于微信/支付宝真实联通。
6. Actuator 指标入口增加内部来源过滤及合同测试，只是后续源码的局部防护。正式机 `/actuator/prometheus` 上次只读为 404，Prometheus/Alertmanager 未运行，P1-06 自动值守仍未成立。
