# 客户独立项目派生规范

## 目标

`mall-swarm-app-h5` 只维护可重复交付的商城基座。每次签约客户都从一个已验收的基座版本派生为独立项目，使用独立代码仓库、服务器、数据库、域名和发布记录。客户制度不得反向写回商城基座。

## 基座负责的稳定能力

- 注册、登录、邀请关系与关系变更审计。
- 商品、订单、支付、库存、发货、收货、售后和退款。
- 支付时冻结订单、商品、上下级关系与客户奖金版本。
- 客户程序先返回并冻结本单奖金，再通过`afterOrder`更新只影响后续订单的客户等级或资格。
- 标准奖金结果落库、防重复、保护期结算、钱包入账与退款追回。
- 通用前后台 UI 框架、版型、品牌、页面和业务入口开关。

## 客户独立项目负责的内容

- 客户奖金制度及其等级、条件、计算顺序、上限和退款口径。
- 普通购买、复购、报单、秒杀等订单类型是否进入客户奖金程序。
- 客户品牌、UI 选择、客户专属页面和业务文案。
- 客户支付、短信、实名、推送等独立外部服务配置。

## 奖金程序接入

客户项目新增一个 `CustomerBonusPolicy` 实现，并使用客户独立的 `policyCode`。输入只能使用基座提供的支付快照，输出统一为奖金接收人、关系深度、客户内部类型编码、比例、金额和审计说明。客户程序不得直接写钱包、修改订单状态或绕开退款追回。

客户程序的输出在写入资金系统前必须通过基座通用校验：接收人编号和类型代码有效、金额与关系深度非负、金额精度明确、同一订单/接收人/类型不重复、审计说明可落库，且本单奖金合计不得超过订单奖金基数。接收人的姓名、账户和当时等级由基座重新读取并冻结，不能由客户程序伪造。客户制度自己的最高拨出率和利润阈值仍需在客户项目中做更严格的验收。

客户制度需要在退款后重算等级、资格或复购状态时，实现同一策略的 `afterRefund` 扩展点。基座会按订单支付时冻结的原规则版本回调，默认策略不进行任何自动调级，避免把某个客户的升级制度带给其他客户。

新客户默认使用 `CUSTOMER_BONUS_DISABLED`：普通购物、支付和售后正常运行，但不生成奖金。历史 `NEW_RETAIL_SIMPLE_DEFAULT` 只为现有测试数据兼容，不得作为新客户默认制度。

## 派生与维护流程

1. 冻结一个通过全量回归的商城基座提交和版本号。
2. 从该提交创建客户独立目录和独立私有仓库，记录来源提交。
3. 先冻结客户制度原文和验收案例，再实现客户奖金程序。
4. 客户 UI 和特殊模块尽量放在客户覆盖区域，避免修改通用订单、钱包与售后核心。
5. 跑通注册/邀请、首购、普通购买、复购、支付、发货、收货、部分退款、全额退款、奖金追回和提现。
6. 独立部署到客户服务器并保留客户自己的备份、回滚和版本报告。
7. 基座公共修复先在基座验证，再按影响选择性同步到客户项目；客户制度改动不得合回基座。

## 禁止事项

- 不在公开商城展示客户奖金制度、比例或招募收益话术。
- 不在通用管理后台提供可随意拼装的奖金公式编辑器。
- 不把一个客户的制度设为所有新客户的默认制度。
- 不复用客户的支付密钥、数据库、域名、短信签名或实名凭据。
- 不通过复制未记录来源的普通文件夹长期维护客户项目。
