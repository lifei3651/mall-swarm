# 客户独立项目派生规范

## 目标

`mall-swarm-app-h5` 只维护可重复交付的商城基座。每次签约客户都从一个已验收的基座版本派生为独立项目，使用独立代码仓库、服务器、数据库、域名和发布记录。客户制度不得反向写回商城基座。

## 基座负责的稳定能力

- 注册、登录、邀请关系与关系变更审计。
- 邀请关系与推广资格解耦，以及关闭、受邀即开通、后台审核、历史首单兼容四种客户级进入方式。
- 商品、订单、支付、库存、发货、收货、售后和退款。
- 支付时冻结订单、商品、上下级关系与客户奖金版本。
- 客户程序先返回并冻结本单奖金，再通过`afterOrder`更新只影响后续订单的客户等级或资格。
- 标准奖金结果落库、防重复、保护期结算、钱包入账与退款追回。
- 通用前后台 UI 框架、版型、品牌、页面和业务入口开关。

## 客户独立项目负责的内容

- 客户奖金制度及其等级、条件、计算顺序、上限和退款口径。
- 客户最终采用哪种推广资格方式，以及该方式需要的资料、审核条件和退出规则。
- 普通购买、复购、报单、秒杀等订单类型是否进入客户奖金程序。
- 客户品牌、UI 选择、客户专属页面和业务文案。
- 客户支付、短信、实名、推送等独立外部服务配置。

## 奖金程序接入

客户项目新增一个 `CustomerBonusPolicy` 实现，并使用客户独立的 `policyCode`。输入只能使用基座提供的支付快照，输出统一为奖金接收人、关系深度、客户内部类型编码、比例、金额和审计说明。客户程序不得直接写钱包、修改订单状态或绕开退款追回。

客户程序的输出在写入资金系统前必须通过基座通用校验：接收人编号和类型代码有效、金额与关系深度非负、金额精度明确、同一订单/接收人/类型不重复、审计说明可落库，且本单奖金合计不得超过订单奖金基数。接收人的姓名、账户和当时等级由基座重新读取并冻结，不能由客户程序伪造。客户制度自己的最高拨出率和利润阈值仍需在客户项目中做更严格的验收。

客户制度需要在退款后重算等级、资格或复购状态时，实现同一策略的 `afterRefund` 扩展点。基座会按订单支付时冻结的原规则版本回调，默认策略不进行任何自动调级，避免把某个客户的升级制度带给其他客户。

新客户默认使用 `CUSTOMER_BONUS_DISABLED`，同时将推广资格方式设为 `DISABLED`：邀请关系仍可安全记录，普通购物、支付和售后正常运行，但不自动开通推广资格，也不生成奖金。历史 `NEW_RETAIL_SIMPLE_DEFAULT` 和 `FIRST_PAID_ORDER` 只为现有商城兼容，不得作为新客户默认制度。

## 新客户安全初始状态

从商城基座首次安装客户项目时，部署入口必须先形成一套可验证、但不会误公开经营内容的安全状态：

- 只能有一个启用中的奖金程序，默认固定为 `CUSTOMER_BONUS_DISABLED`；没有完成客户制度开发和全流程验收前，不允许产生奖金。
- 推广资格默认固定为 `DISABLED`；客户确认后可选择受邀即开通或后台审核，首笔有效订单方式必须单独复核业务与合规要求。
- PV、团队业绩、奖金来源、奖金流水等内部经营信息默认隐藏；客户项目完成制度设计后，再按该客户的权限和端形态决定是否展示。
- 基座附带的演示分类、轮播、公告、商品和规格只保留为后台草稿，不直接出现在客户域名；正式上线前必须由客户资料替换并人工启用。
- 初始化脚本以“该客户尚无任何奖金版本”为首次执行边界。只要客户项目已经存在任一奖金版本，重复部署或升级不得改写其展示设置、商品状态或制度版本。
- 通过后台新增客户时采用同样的默认值，避免命令行部署和管理后台创建出现两套安全口径。

## 派生与维护流程

1. 冻结一个通过全量回归的商城基座提交和版本号。
2. 使用`document/customer-project/scripts/derive-customer-project.sh`从该提交生成客户独立目录；禁止手工复制工作区。工具会移除基座生产目标、历史发布物和未提交内容，生成来源清单与独立Git初始提交，但不会配置远程或服务器。
3. 先冻结客户制度原文和验收案例，再实现客户奖金程序。
4. 客户 UI 和特殊模块尽量放在客户覆盖区域，避免修改通用订单、钱包与售后核心。
5. 先验证默认关闭程序下注册、一次性邀请绑定、购买、支付、发货、收货和售后均可运行且推广资格不自动开通、奖金为零，再跑通客户确认的资格方式及制度下的首购、普通购买、复购、部分退款、全额退款、奖金追回和提现。
6. 独立部署到客户服务器并保留客户自己的备份、回滚和版本报告。
7. 基座公共修复先在基座验证，再使用`document/customer-project/scripts/upgrade-customer-project.sh`对客户项目执行只读三方预检；无冲突时才允许应用，客户制度改动不得合回基座。

## 派生工具门禁

- 目标目录必须不存在并位于商城基座仓库之外，避免覆盖既有项目或把客户仓库嵌入基座。
- 来源必须是一个明确、已提交的Git提交；当前工作区的未提交文件不会进入客户项目。
- 新项目不继承基座`.git`、远程仓库、生产服务器目标、历史远程发布脚本、发布包、审计截图、日志或XMind。
- Android接口、支付宝回调和Nginx客户域名使用不可发布的安全占位值；客户正式资料确认前不能发布。
- 新项目只保留完成构建、私有部署和本地安全验证所需的通用脚本；初始Git仓库只有一条提交且没有远程。
- 每次调整派生规则后，必须运行自动派生门禁，并至少用一个临时客户项目完成后端、公开商城、团队H5、一体化H5和管理后台全量构建。
- 客户项目升级只允许从来源清单记录的旧基座提交前进到其后代提交；禁止降级、跨历史覆盖、在基座或客户脏工作区执行，或通过任一等价地址把客户远程指向商城基座。
- 升级发生冲突时整次停止并保持客户工作区不变；正式应用只更新文件和来源清单，不自动提交、推送、迁移数据库或发布。

## 禁止事项

- 不在公开商城展示客户奖金制度、比例或招募收益话术。
- 不在通用管理后台提供可随意拼装的奖金公式编辑器。
- 不把一个客户的制度设为所有新客户的默认制度。
- 不复用客户的支付密钥、数据库、域名、短信签名或实名凭据。
- 不通过复制未记录来源的普通文件夹长期维护客户项目。
