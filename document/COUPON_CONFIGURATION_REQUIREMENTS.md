# 优惠券后台配置与影响确认要求

更新时间：2026-09-12。状态：需求约定，尚未实现或上线；不得以本文件代替资金链路验收。

## 用户已明确的要求

- 增加优惠券，商家商品也要参与，不局限于平台自营。
- 平台发放的券可以限定平台全部或指定部分商品；也需要支持指定某一商家的全部商品，或该商家的单个指定商品。
- 优惠券相关规则应在后台配置，不把全部优惠成本固定扣在商家身上，也不由开发者替运营确定承担比例。
- 在配置过程中弹窗提醒：优惠券会影响商家结算及团队奖金。用户原话中的“上架结算”结合上下文按“商家结算”处理。
- 此弹窗属于有实际影响的风险确认，不新增普通保存成功“知道了”弹窗。

这次明确的是“后台可配置并确认影响”，不是确认某一承担比例、奖金基数或对历史订单重新计账。

## 拟实现的配置结构

1. 券本身：优惠额度、使用门槛、有效期、发放/每人领取限制和适用商品、商家范围。
2. 成本承担：平台承担、商家承担、按比例共同承担；明确比例合计、适用商家范围和变更生效范围。未明确配置不得发放/启用，不能以隐式默认值使商家收入发生扣减。
3. 团队奖金：必须明确参与奖金的业务范围和计算基数。优惠前商品金额、优惠后商品实付等选项需写清财务含义并与现有奖金引擎逐项核对，不能只提供含糊的“影响奖金”开关。
4. 配置页同步显示规则摘要与影响测算。测算是预览，不产生订单、结算、奖金或资金流水。

以上为功能设计方案，不表示当前代码已有配置表单、领取、抵扣或退款能力。配置枚举的具体算法仍需在实现阶段完成一致性设计与回归，未经选择不得替客户自动启用。

## 商品适用范围（用户补充）

“发放方”“适用商品归属”“优惠成本承担方”分别建模。平台发券不等于可以抵扣所有商家的商品，也不自动意味着由平台承担全部优惠。此次仅明确商品适用范围，不据此给商家账号新增发券或跨店配置权限。

本轮把“平台商品”按平台自营商品理解；后台文案明确使用“平台自营全部商品”，避免被理解为包含所有入驻商家的全商城通用券。

| 适用范围选项 | 后台配置 | 使用边界 |
| --- | --- | --- |
| 平台自营全部商品 | 选择平台自营＋全部商品 | 不包含入驻商家商品 |
| 平台自营指定商品 | 选择平台自营＋勾选商品，可选一个或多个 | 仅已选商品，其他自营商品也不可用 |
| 指定商家全部商品 | 先选一个商家，再选全部商品 | 仅该商家的商品，不包含平台或其他商家 |
| 指定商家指定商品 | 先选一个商家，再选商品，支持只选一个 | 仅该商家的已选商品；同一选择器支持多选作为部分商品配置方案 |

后台配置流程：选择归属范围 → 全部/指定商品 → 指定范围时勾选商品 → 配置优惠与成本/奖金规则 → 查看影响并确认。切换平台/商家或商家主体时，不可保留原归属的商品选择。指定商品为空时禁止启用，不允许空列表被解释为全部。

前台券卡与使用说明直接展示“平台自营通用”“平台指定商品可用”“某商家店铺通用”或“某商家指定商品可用”，并提供对应的可用商品列表。结算时明确说明不可用原因，而不是让用户猜测范围。

拟定实现校验：

- 按稳定商品ID及归属匹配，不能用商品名称或前端传来的商家标记判断；指定商品必须真实属于所选平台/商家和当前商城。
- “全部商品”表示使用时符合该归属的商品范围；新增同归属商品也可参加，后台需说明这一点。“指定商品”仅按勾选ID匹配，不随新增商品自动扩展。
- 混合购物车只有命中范围的商品参与门槛与抵扣，不可用其他商家商品或运费凑门槛，也不可把优惠分摊到不适用商品。此为拟定门槛计算方案，须在后台文案及实现验收中明确，不改当前交易算法。
- 商品下架、不可售、归属变化或规则版本变化，报价与下单需重新校验；选择器展示不等于最终可核销。
- 后续修改规则不能覆盖既有订单快照；券实例与模板采用可追踪规则版本，不能把已领取券静默缩小范围，具体变更流程需在发券实现中确定。
- 验收至少覆盖上述四种范围、单商品券、空选择、非法跨店商品ID、混合购物车及新增商品边界；两端显示与后端判定一致。

## 保存/启用确认

涉及资金规则的首次保存、承担方/比例/奖金口径等实质修改，以及启用时，明确展示确认弹窗；同一次提交不得重复弹窗。普通浏览、无变化保存与单纯成功反馈不重复打断。

标题：确认优惠券影响

提醒：本次优惠券配置会影响参与订单的商家结算及团队奖金。请核对优惠承担方、分摊比例、适用范围及奖金计算口径，确认无误后再继续。

弹窗必须带入本次配置的具体摘要，包括平台/商家名称、全部/指定商品及已选商品数量、承担方/比例和奖金口径，不能只展示固定文案；提供“返回修改”和“确认保存”或“确认启用”。取消不得保存或生效。表单或后台配置版本在确认期间变化时必须重新核对，不能使用过期确认结果。

保存成功仅更新页面状态或非阻断反馈，不再弹第二个成功确认框。草稿保存与正式启用应有清楚区别，不得把“确认保存”自动解释为已发券或已经产生财务影响。

## 实现前后必须保持的边界

- 后端重新校验权限、适用范围、规则完整性及当前配置版本，不能仅依赖前端弹窗阻止异常提交。保留操作人、时间和规则版本审计。
- 金额使用精确分值分摊，明确商品项/商家子单/父交易合计；消费者优惠、商家承担及平台承担可逐项对账。
- 订单保留下单时优惠、承担和奖金规则快照；后续配置修改不得追溯覆盖已有订单及其售后依据。
- 团队奖金仅作用于原本具备奖金资格的业务，优惠券不能把普通商城订单变成可分佣订单，也不能绕过既有奖金资格/上限。
- 领取、占用、支付核销、取消释放、到期、部分退款与多次退款必须作为同一功能完整验证；不得只发后台表单而宣称优惠券已可用。
- H5、小程序、后台共用后端规则，客户端只展示明细和提交选择；重复请求、跨商家/跨租户越权与并发核销需要测试。
- 首次启用前应以自营、至少两个商家、混合购物车和退款样例核对消费者实付、商家结算、平台承担及团队奖金。不得操作真实资金替代隔离测试。
