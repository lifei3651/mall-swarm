## 构建方式

商城前端从同一套受控源码产生两个相互独立的静态包：

```bash
cd mall-shop-web
npm run build:public
npm run build:team
```

- `dist/`：公开商城包，构建结束自动扫描团队文字、路由和接口；发现邀请、团队、奖金、提现、复购等内容会直接构建失败。
- `dist-team/`：团队 H5 包，只包含团队业务页面。
- Android Capacitor 始终使用公开商城 `dist/`，不会打入团队 H5。
- 微信小程序不是网页构建产物，客户确定上架需求后必须新增独立小程序前端，复用 `/shop/public/**` 及普通商城接口。

## 账号和奖金边界

两端共用同一会员账号体系，但不因公开购物自动加入团队：

1. 公开商城调用 `/shop/public/auth/register`，服务端强制忽略任何关系参数，写入 `team_opt_in=0`。
2. 公开账号支付普通订单时，不创建代理身份，不冻结团队关系，不产生团队业绩和佣金。
3. 会员进入团队 H5 后，可使用同一账号登录；未建立关系时必须输入邀请码并确认一次。
4. 关系确认使用会员行锁和数据库条件更新，绑定后本人不能重复修改。
5. 团队 H5 邀请注册直接写入 `team_opt_in=1`；其首笔符合规则的有效订单才激活团队会员并进入奖金链路。
6. 原一体化商城的历史会员在迁移时保持团队资格，不删除、不重算历史关系、业绩或奖金。

## 部署边界

客户部署必须提供两个不同域名，例如：

- 公开商城：`mall.customer.com`
- 团队 H5：`team.customer.com`

部署包将静态文件分别放在 `html/public`、`html/team`、`html/admin`。Nginx 对不同域名使用不同静态根目录，因此公开域名无法通过猜测 `/team` 路径下载团队构建。证书必须覆盖公开商城、团队 H5 和后台域名，CORS 必须明确列出这些 HTTPS 来源。

## 可选多商户模块

- 多商户直接叠加在这套拆分核心上，不再复制第三套项目；不启用时，现有商品和订单继续按平台自营运行。
- 商品可绑定一个商户，订单只允许同一商户或平台自营商品结算，避免运费、售后、发票和货款责任混在一张订单里。
- 商户货款按下单时保存的成本单价乘有效数量计算。例如成本价 50 元、有效销售 10 件，应结货款为 500 元；平台不另收服务费。
- 支付后先进入“待结算”，订单确认收货、客户配置的售后期限结束且没有进行中售后后转为“可提现”。退款按原成本快照冲回；已提现后发生退款时形成商户欠款，后续货款优先抵扣。
- 财务流程为“申请提现 → 冻结余额 → 登记发票/调整 → 确认实际打款或驳回”。系统不设置“扣税”字段，只保存通用调整金额与原因，避免系统替财务作税务判断。
- 商品销售区分为普通商城、复购区、报单区三个独立开关；团队奖金模式分为继承原规则、不发团队奖、标准团队奖、客户定制。标准团队奖商品只允许进入复购区或报单区，客户定制规则未实现前拒绝下单。
- 当前基座由平台后台维护商户、商品归属和货款申请，尚未开放独立商户登录门户；若客户需要商户自行登录、上架、发货和申请提现，应作为下一阶段增加商户账号、数据隔离和审核流，不能直接复用平台管理员权限。

详细规则见 [《多商户业务设计》](./MULTI_MERCHANT_DESIGN.md)。
