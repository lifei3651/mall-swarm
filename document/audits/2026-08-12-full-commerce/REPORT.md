# 商城基座全链路产品与测试审计

- 审计日期：2026-08-12
- 审计对象：`1.0.47` 本地待发布版本
- 当前线上：`1.0.46`
- 定位：客户交付前的商城基座，不按正式生产商城处理测试商品、测试订单和占位资料
- 审计原则：不提交真实订单、不发起真实支付/退款/提现、不绕过验证码、不改线上数据

## 一、结论

正常商城主链路已经具备可用基座：浏览商品、登录注册、购物车、确认订单、订单中心、售后申请、客服处理、品牌配置、经营资质入口和特殊商城开关均已形成闭环。本轮实际走查确认并修复了 3 个会造成业务误判或客户品牌串用的问题：

1. 未接入真实物流轨迹时，订单详情错误显示“运输中”；现已改为只陈述系统确定知道的“已发货”和发货时间，并明确实际轨迹以承运商查询结果为准。
2. APP 下载页图标写死为 `LQ`；现已读取后台客户 Logo，客户后续更换商城资料 Logo 后会自动同步。
3. 后台人工退款入口仍自行按下单后 7 天判断；现已统一读取服务端的售后模式、截止时间及 0 天关闭开关，不再与后台配置冲突。

本轮没有改变用户已明确要求保留的售后业务模式，也没有发布服务器。`1.0.47` 仍是待发布版本。

## 二、全链路健康度

### 1. 首页、分类、搜索、商品详情：健康

- 首页品牌、搜索、公告、分类、商品卡和底部导航结构清晰，移动端信息层级正常。[首页截图](screenshots/01-storefront-home-mobile.png)
- 分类搜索、排序、分类切换和加购入口在同一页面完成，未出现横向溢出或操作遮挡。[分类截图](screenshots/02-category-search-mobile.png)
- 商品详情的 SKU、数量、库存/限购、加入购物车和立即购买具备前后端双重校验；本轮未发现新的业务缺陷。
- 测试商品、测试分类和测试公告属于当前基座验收数据，不作为“生产数据污染”缺陷；客户交付前再按交付清单统一清空或替换。

### 2. 登录、注册、找回密码：健康

- 登录后回到原目标页面，游客不能先写入购物车再到结算时才被拦截。
- 注册协议是真实 checkbox，登录、注册和找回密码字段具有语义标签，键盘和读屏基础能力已具备。[注册截图](screenshots/13-register-accessibility-mobile.png)
- 图形验证码属于安全边界，本轮没有绕过后台验证码进入受保护页面。

### 3. 购物车与确认订单：健康，真实资金未验收

- 商品数量、规格、价格、PV 和结算金额关系清楚；购物车不会混入秒杀或复购商品。[购物车截图](screenshots/05-cart-filled-mobile.png)
- 确认订单包含收货地址、客户订单备注、支付方式、商品和金额汇总；未点击“提交订单”，没有制造写入和真实资金动作。[确认订单截图](screenshots/06-checkout-mobile.png)
- 支付宝、微信、余额支付的正式小额订单、重复回调、超时关闭、退款和对账仍需用户在客户支付参数就绪后单独验收。

### 4. 个人中心、钱包、团队、邀请：健康

- 订单待办、余额、业绩、支付安全、地址和邀请入口层级明确；小屏页面没有明显遮挡。[个人中心截图](screenshots/07-profile-mobile.png)
- 余额、奖金、业绩和提现属于高风险资金域，本轮只验证页面与代码，不执行真实转账或提现。

### 5. 订单与售后：健康

- “退款/售后”分页只展示仍有处理意义的记录；已取消申请及“不想要了”等原因不再污染全部订单表格。[售后列表截图](screenshots/08-orders-after-sale-mobile.png)
- 售后详情展示申请金额、商品、处理进度和可取消状态，客户与客服所见职责清楚。[售后详情截图](screenshots/09-order-detail-after-sale-mobile.png)
- 售后规则继续支持“签收后起算 / 下单后起算”和 0～365 天，本轮没有擅自修改客户规则；后台人工退款改为与服务端配置保持一致。
- 后台订单末尾已有仅客服可见备注，并与客户下单留言分开保存、搜索和审计。

### 6. 物流：基础发货闭环健康，真实轨迹待接入

- 修复前，只有物流公司和运单号却显示“运输中”，容易让客户误以为系统已经获取承运商扫描事件。[修复前截图](screenshots/10-order-logistics-mobile.png)
- 修复后，只显示“已发货”、发货时间和“查询承运商”，不再伪造运输进度。[修复后截图](screenshots/15-order-logistics-fixed-desktop.png)
- 当前支持后台单笔发货、批量导入、拆包/合箱、复制运单号和跳转第三方查询；还没有本地物流事件时间线。
- 推荐做法不是提前硬接多家未知服务商，而是先固定统一 `LogisticsProvider` 接口和事件模型；客户确定已有商城所用服务商并提供 API 文档、账号、回调签名方式后，优先接入同一家，再按相同接口扩展第二家。

### 7. 品牌、APP 与经营资质：基座健康，客户资料待配置

- APP 页原固定 `LQ` 图标已改为读取后台客户 Logo。[修复前截图](screenshots/11-app-download-mobile.png) / [修复后截图](screenshots/16-app-download-fixed-desktop.png)
- Android 内测版本仍保持不公开，页面不会暴露 APK 地址、测试版本号或校验值。
- 经营资质页和首页公开入口已存在；当前占位主体、信用代码和地址符合“基座”状态，不视为缺陷，但客户交付前必须配置真实资料。[经营资质截图](screenshots/12-business-license-mobile.png)
- 经营资质不必塞入每个页面底部；首页页脚保留“经营资质”入口即可，同时用户协议、隐私政策、下单确认页应能访问主体和售后规则。这比在所有页面反复堆叠营业执照信息更清晰。

### 8. 管理后台：代码与回归健康，受保护页面本轮有证据限制

- 登录页已经明确区分“软件开发与技术服务方”和“商城经营主体”，客户 Logo 由商城资料控制。[后台登录截图](screenshots/14-admin-login-desktop.png)
- 本轮未人工识别或绕过图形验证码，因此没有进入受保护后台逐页点击；后台订单、商品、会员、财务、经营设置等页面使用源码、接口和 77 项前端回归测试交叉验证。
- 后续正式验收应由有权限的管理员正常登录，再补一次页面级回归和权限矩阵检查。

### 9. 秒杀与复购商城：基座完成，默认关闭

- 秒杀订单使用独立入口、库存抢占、限流、幂等和业务类型，不能与普通购物车混单；真正大并发上线前仍需在客户服务器规格上做压测和故障演练。
- 复购商城使用独立商品池、价格、PV、限购和准入，不与正常商城订单混单；奖金规则默认为不参与，客户定制规则未验收时禁止下单。
- 两类业务都应继续保持租户级开关关闭，只有客户合同、业务制度、奖金口径和验收用例明确后才开启。

### 10. ERP、发布与本地环境：框架具备，客户集成待定

- ERP 已有适配器、任务、重试、回调和人工补偿框架；不应在客户未确定 ERP 时盲目实现几套具体字段映射，否则会形成不可验证的伪集成。
- 建议先锁定统一订单、商品、库存、发货和售后数据契约；客户确定服务商后只新增对应 adapter、签名和映射。
- 本机现有 MySQL 测试库结构落后于当前源码，本轮浏览器验收采用隔离 H2 数据库，没有擅自改动用户本地库。后续本地联调前，应从标准初始化结构恢复或在备份后完成全量结构对齐。
- 线上仍为 `1.0.46`；`1.0.47` 的秒杀/复购及客服备注迁移必须先备份、执行迁移、发布，再做版本与数据计数核验。

## 三、本轮确认的优势

- 普通、秒杀、复购三类交易来源隔离，避免价格、库存、PV 和奖金互相串单。
- 前后台共用服务端售后截止时间，0 天、签收后和下单后模式都有明确语义。
- 客户下单留言与客服内部备注分离，客服备注不返回客户且有操作审计。
- 商城和后台的新会话均不再长期保存在浏览器本地存储，关键写操作具备幂等、限流或状态锁。
- 经营主体、品牌、协议、页面模块和特殊业务都以客户配置为中心，符合“一套基座、按客户交付”的产品定位。

## 四、交付前全局规划

### P0：每个客户必须完成的交付闸门

1. 配齐品牌 Logo、商城名、经营主体、信用代码、地址、电话、邮箱、营业执照、备案和客服时间。
2. 确认支付通道商户、回调域名、密钥托管和退款责任人，完成真实小额全链路验收。
3. 确认售后起算模式、天数、退货地址、运费承担、人工退款权限和客服话术。
4. 确认奖金制度版本、适用订单类型、退款冲正和财务对账口径。
5. 完成数据库备份、迁移演练、回滚演练、版本身份和核心数据计数核对。

### P1：外部能力接入

1. 物流：建立统一事件表、订阅/查询任务、回调验签、幂等去重和前台时间线；先接客户正在使用的服务商。
2. ERP：按统一数据契约接一个真实 ERP，覆盖推单、库存、发货、取消、退款和失败补偿。
3. 短信：实名模板、签名、费用告警、失败重试和客户投诉处理。
4. 可观测性：在客户服务器开启错误、慢查询、Redis、连接池、库存、支付回调和定时任务告警。

### P2：客户选择性功能

1. 秒杀压测、排队页、活动监控、风控名单及运营复盘。
2. 复购资格、价格、PV、周期、限购和奖金制度的客户定制。
3. 多仓、电子面单、自动审单、客服工单、发票和会员积分等扩展模块。

## 五、无障碍与视觉结论

- 注册协议 checkbox、表单标签、数量按钮名称和确认弹窗角色已经具备基础语义。
- 首页、分类、购物车、结算、个人中心和售后列表在 390×844 截图中未发现明显横向溢出、按钮遮挡或关键信息截断。
- 后台登录页在桌面尺寸下层级清楚；受验证码限制，本轮不能把后台所有受保护页面的视觉状态描述为“实机全部通过”。
- 商品详情全页长截图出现浏览器拼接裁切，因此没有把该截图作为视觉结论依据；商品详情功能由页面结构、DOM 和回归测试核验。
