# 第十八轮 Cookie、API 与输入安全复核报告

审查日期：2026-08-22

审查对象：`mall-swarm-app-h5`（App / 小程序公开商城 + 团队 H5 拆分基座，同源可选一体化 H5）

审查方式：仅核查本地代码、配置、前后端调用协议和自动化测试；未访问线上、未执行漏洞利用、未修改线上数据。

## 结论

原报告列出的 15 项不等于 15 个已验证漏洞。逐项沿真实请求链复核后：1 项是会影响后台正常操作并同时缺少输入边界的真实缺陷，已修复；3 项属于值得收口的防御性配置或边界校验，已完成；其余 11 项是已有保护、刻意的批量业务语义、正确的浏览器安全设计或没有具体可利用证据的泛化建议。

本轮没有发现可利用的 XSS 或 SQL 注入路径，也没有发现能够绕过商城 Cookie 写请求 CSRF 防护的路径。商城安全 Cookie 在 HTTPS 下保留 `SameSite=None`，这是原生 App 跨站 API 会话的兼容要求；其防护依赖的是“精确 HTTPS CORS 白名单 + 非简单自定义请求头 + 服务端写请求强制校验”，不是单独依赖 Cookie 属性。

## 逐项复核

| 编号 | 结论 | 证据与处理 |
| --- | --- | --- |
| M1 | 报告定级不成立，保持现状 | `SameSite=None; Secure; HttpOnly` 用于 Capacitor App 从本地安全源访问公网 API。恶意表单不能附带 `X-Shop-Client: storefront`，缺头的 Cookie 写请求在进入业务前返回 403；带自定义头的跨站请求会先触发预检，后端只允许部署时明确登记的精确 HTTPS Origin。回归同时证明合法 App/H5 写请求仍可进入业务链。 |
| M2 | 已加固 | 基础 `application.yml` 明确设置 Sa-Token 只读 `Authorization` 头、不读普通 Cookie，并补齐 Secure/HttpOnly/Strict 默认 Cookie 属性；生产覆盖保持一致。实际商城和后台会话仍由各自专用 HttpOnly Cookie 服务管理。 |
| M3 | 不构成当前漏洞 | 外部客户端已经统一使用 `/api/v1`，Nginx 负责兼容映射到同一后端控制器；旧 `/api` 是明确记录的兼容入口。版本生命周期属于网关契约，不要求为了形式复制全部 Controller。 |
| M4 | 条件加固完成 | 两个人工结算写入口当前均被业务层固定禁用，不存在佣金提前结算路径；仍补充批量编号数量/正数约束、结算批次备注长度及 `@Valid`，防止未来重新启用时带入无边界输入。 |
| M5 | 已验证缺陷并修复 | 管理后台原来用查询参数发送 `cancelReason`，后端却按原始请求体读取，正常取消佣金可能报缺少请求体。现统一为受校验的查询模型，原因必填、最多 200 字，前端同步校验和去除首尾空格；服务层再次校验并不再把原始原因写入普通日志。 |
| M6 | 报告遗漏现有保护，不改业务语义 | 列表导入由 `ImportServiceImpl` 在服务层统一限制非空、最多 5000 行，并对每一行调用 Jakarta Validator；无效行进入导入结果而不影响合法行。这是运营需要的逐行结果设计。若在 Controller 对整个 List 使用 `@Valid`，一行错误会让整批直接 400，反而破坏既有部分成功/失败明细。 |
| M7 | 不可利用并进一步收口 | 财务手填退款端点固定返回“必须从订单售后发起”，从未调用 `saveRefund`；本轮移除该禁用入口对 `FinanceRefundDTO` 的解析，任何请求体都不能进入财务写服务。真正售后退款继续由订单、售后、金额、数量和行锁链路生成内部 DTO。 |
| M8 | 原利用描述不成立，边界已加固 | 服务层原本已经拒绝空值和小于等于 0 的订单金额；本轮再给模拟 DTO 增加正数 ID、会员字段长度、金额 0.01～99.99999999 亿元和两位小数约束，并在 Controller 启用 `@Valid`。 |
| L1 | 已有治理 | API 指南已明确 `/api/v1` 为新客户端入口、`/api` 为旧客户端兼容入口；后续不兼容变更必须新增版本而非静默改变旧契约。 |
| L2 | 不作为安全漏洞修改 | 商品目录是公开数据，且商品、库存和资格可能按会话变化。当前由服务端短时目录缓存控制数据新鲜度，不在共享 HTTP 缓存层强制公共缓存，避免把个性化结果误缓存给其他用户。 |
| L3 | 已加固 | 基础和生产配置均显式声明 `is-read-header: true`。 |
| L4 | 正面安全属性 | 不设置 Cookie Domain 会生成 host-only Cookie，减少子域共享和被弱子域利用的范围；不是缺陷。 |
| L5 | 缺少具体证据 | 报告没有给出可达端点、参数或资源消耗证据。现有敏感搜索字段、分页、导入、文件和业务 DTO 已有具体边界；不对所有字符串使用一个会破坏地址、备注、订单号等合法输入的统一上限。 |
| L6 | 正面结论 | 公告继续使用 Vue 文本插值转义，不使用 `v-html`；若未来确需富文本，必须引入独立白名单净化和回归测试。 |
| L7 | 安全生成模式 | MBG Example 的 `${criterion.condition}` 只来自服务端生成的受控条件对象，不接受请求文本；现行业务 SQL 均使用参数绑定，没有发现用户输入到该模板的传播路径。 |

## 修复后的安全不变量

1. Cookie 认证的商城写请求缺少固定客户端头时，业务服务不会执行。
2. 精确登记的 App/H5 客户端仍可携带 HttpOnly Cookie 完成正常写请求，不因收紧 SameSite 而掉登录。
3. 后台取消佣金的前后端协议一致；空白、超过 200 字的原因在业务执行前被拒绝，服务层调用也不能绕过。
4. 手填财务退款入口始终不能修改资金；真实退款只能由订单售后状态机生成。
5. 奖金模拟不能接受负数、零金额、超大金额或超长会员字段。
6. 批量导入继续按行反馈错误，不因单行 DTO 校验失败而丢失整批运营结果。

## 验证结果

- Cookie、配置和输入边界专项：20/20 通过。
- 后端完整回归：公共模块 14/14、分销模块 423/423，共 437/437 通过。
- 管理后台：110/110 通过，生产构建成功。
- 后端编译成功；差异格式检查通过。
- 完整回归额外暴露并修复一项既有测试不稳定：原密文篡改测试只替换 Base64 最后字符，某些无填充编码下可能仍解码为同一字节；现改为翻转真实密文字节，稳定验证 AES-GCM 篡改必定失败。生产加解密逻辑未改变。
