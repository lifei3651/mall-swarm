# 第十六轮安全审查复核报告

审查日期：2026-08-22

审查对象：`mall-swarm-app-h5`（App / 小程序公开商城 + 团队 H5 拆分基座，同源可选一体化 H5）

审查方式：仅核查本地代码、配置、测试与部署模板；未访问线上、未执行漏洞利用、未修改线上数据。

## 结论

原报告共列出 23 项。逐项回到真实调用链后：7 项属于需要修复或加固的真实问题，已全部完成；其余 16 项为正确设计、已有保护、尚未实现的未来适配器要求，或不具备可利用性的泛化建议。此次没有数据库结构迁移，版本继续为本地 `1.0.75` 待发布，线上保持 `1.0.74`。

本轮优先修复支付回调收款主体校验和商城登录回跳，其次补齐第三方 SDK 超时与调度容量。没有把浏览器路径、公开 404、CSP meta、`@Async` 数量等表现指标误判成安全边界。

## 逐项复核

| 编号 | 复核结论 | 证据与处理 |
| --- | --- | --- |
| ROUTE-001 | 不构成漏洞 | 管理后台使用 History 路由只会公开页面路径，路由名不是秘密；接口仍由服务端会话、权限与商户作用域授权。改成 Hash 不能保护后台接口，反而会破坏现有 Nginx 回退及入口地址。 |
| ROUTE-002 | 正确设计 | 公开 404 只渲染 `NotFound.vue`，不读取后台数据，也不会绕过任何接口权限；未登录用户看到“页面不存在”是正常产品行为。 |
| ROUTE-003 | 有条件保留 | 旧 Token 启动时立即从 `localStorage` 删除，只短暂保存在页面内存，用于换发 HttpOnly Cookie；它是版本升级兼容桥，不是长期持久会话。待确认所有客户已跨过升级窗口后可整段删除。 |
| STATE-001 | 报告误判 | Cookie 认证的写请求已由 `ShopSessionCookieFilter` 和 `AdminSessionCookieFilter` 强制校验 `X-Shop-Client` / `X-Admin-Client`，跨站页面无法在严格 CORS 下自行附加该头；Cookie 同时为 HttpOnly/SameSite。当前采用自定义头型 CSRF 防护，无需再叠加一套表单 Token。 |
| STATE-002 | 已修复 | 三种商城登录入口与支付密码修改后的回跳统一走 `safeShopRedirect`；只允许规范的站内绝对路径，拒绝协议相对地址、反斜杠、控制字符、双重编码和登录/注册循环。 |
| STATE-003 | 有条件保留 | SSE 读取的旧 Token 与 ROUTE-003 是同一个仅内存迁移桥；持久副本在读取后已清除。正常新会话使用 HttpOnly Cookie。 |
| STATE-004 | 报告误判 | 生产 Nginx 已发送 CSP HTTP 响应头，能力强于 HTML meta；重复添加 meta 不会强化后端接口，也不能覆盖所有 CSP 指令。 |
| STATE-005 | 不应前端修复 | 返回数据脱敏必须由服务端完成，前端不是可信边界。当前账号、手机号、实名、银行卡和操作日志敏感字段已在服务端按权限输出脱敏 VO。 |
| STATE-006 | 已有保护 | Vite 生产构建默认不生成 source map，发布前安全脚本还会扫描并拒绝 `.map` 文件；无需为了形式重复配置。 |
| STATE-007 | 正确设计 | `checkout_draft` 只保留地址 ID、支付方式和最多 500 字订单备注，不再保存姓名、电话或完整地址；使用 sessionStorage 是为了从地址页返回时恢复当前结算。 |
| STATE-008 | 已加固 | `shop_member` 从本轮起仅缓存会员 ID 和昵称，移除登录账号；它只用于页面展示，认证和权限始终以服务端 `/me` 为准。 |
| 3RD-001 | 已修复 | 支付宝异步通知在验签后、读取订单前，增加签名参数 `seller_id` 与配置商户 PID 的恒等校验；生产启用支付宝时强制配置 `ALIPAY_SELLER_ID`，缺失即拒绝启动。原有 `app_id`、订单金额、交易状态、行锁与幂等校验继续保留。 |
| 3RD-002 | 已修复 | 阿里云短信客户端增加可配置连接/读取超时，默认 5 秒/10 秒，并限制到合理区间，避免第三方网络异常长期占用业务线程。 |
| 3RD-003 | 当前不可利用 | 现有三个 ERP 适配器都是禁止启用的接口基座，`orderPushReady()` 固定返回 false，没有任何向配置 endpoint 发 HTTP 的实现，因此当前不存在 SSRF 请求落点。未来接入客户真实 ERP 时，必须在实际请求层做 DNS/IP 解析后校验，并按客户专线或内网地址建立显式 allowlist，不能一刀切禁用所有内网地址。 |
| 3RD-004 | 已修复 | 支付宝 SDK 客户端增加可配置连接/读取超时，默认 5 秒/10 秒；查询、支付、退款共用同一受限客户端。 |
| TASK-001 | 报告误判 | Redis 缓存监控只采集当前实例的本地指标并执行轻量 ping，多实例各自采样才是正确含义；加分布式锁会导致其余实例失去自身指标。 |
| TASK-002 | 已修复 | Spring 调度线程池由默认单线程改为 4 线程，可通过 `SCHEDULING_POOL_SIZE` 配置，并启用优雅停机等待；长任务不再天然阻塞所有短任务。业务级分布式锁继续防止多实例重复写。 |
| TASK-003 | 已有保护 | `LineChangeScheduler` 调用的服务按单条捕获异常，外层分布式任务执行器在 `finally` 释放锁；外层异常也会由 Spring 记录，不存在静默丢锁。 |
| TASK-004 | 不采纳 | 强制中断数据库或第三方调用可能留下半完成状态，比超时本身风险更高。当前采用有限批次、数据库/SDK 超时、租约锁、幂等状态机和失败重试；后续真实外部适配器应在客户端设置超时，而不是强杀 Java 线程。 |
| TASK-005 | 已优化 | ERP 重试和奖金扫描周期从硬编码改为 `ERP_SYNC_SCAN_INTERVAL_MS`、`BONUS_CALCULATION_SCAN_INTERVAL_MS`，客户部署可按规模调整。 |
| TASK-006 | 报告误判 | SSE 队列拒绝会明确记录告警，不是静默丢弃；SSE 只发送“数据变化”刷新信号，订单查询接口才是权威状态，因此允许在过载时丢失非关键提示。 |
| TASK-007 | 已有保护 | 三个结算子任务已有独立 `try/catch`，底层按单据独立事务；首项失败不会阻止后两项，相关回归测试已覆盖。 |
| TASK-008 | 不构成问题 | 未使用 `@Async` 不是漏洞。调度线程池、分布式锁和明确事务边界比任意异步化更可控；随意增加异步会削弱错误传播与资金任务顺序。 |

## 本轮实际改动

1. 商城站内回跳统一白名单校验，并补齐编码绕过、外部地址和登录循环测试。
2. 支付宝配置新增收款商户 PID、连接超时和读取超时；异步通知校验 `seller_id`，部署门禁及客户交付清单同步更新。
3. 阿里云短信 SDK 增加连接/读取超时。
4. 调度器改为可配置多线程池，ERP 与奖金扫描周期改为部署变量。
5. 浏览器会员快照移除登录账号，只保留页面所需的 ID 和昵称。
