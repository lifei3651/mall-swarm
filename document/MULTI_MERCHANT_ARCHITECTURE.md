# 多商户业务闭环设计与实施边界

更新日期：2026-08-19
适用仓库：App + 团队 H5 拆分版商城基座

## 1. 产品结论

多商户不是一套孤立的新商城，而是在现有商城基座上增加六个相互约束的中心：

1. 商户中心：准入资料、合同、收款与开票资料、账号及退出管理。
2. 商品中心：商品归属、销售价、结算价、结算周期、地址、审核版本与上下架。
3. 订单履约中心：按商户隔离订单、发货、物流、客服备注与历史履约。
4. 售后中心：按商户处理申请，退款结果统一进入平台资金与商户货款冲回。
5. 资金结算中心：待结算、可提现、提现冻结、保证金、欠款和累计打款。
6. 风控权限中心：会话绑定商户、后端查询隔离、业务状态控制和操作审计。

核心原则是 `tenant_id + merchant_id + 权限 + 状态机 + 业务快照 + 资金总账`，不能只依靠前端隐藏菜单。

### 1.1 客户租户与商户的边界

当前交付模式是“每个客户一套独立部署、独立数据库和密钥”，不是多个客户共用一个数据库的 SaaS。`tenant_id` 表示客户级配置和商城数据范围；`merchant_id` 表示同一客户商城内的入驻商户。

因此，代理、会员、奖金和平台管理员是该客户整体的平台数据，不按入驻商户复制一份。商户账号通过后端权限矩阵无法访问这些平台模块；商户可使用的商品、订单、售后、地址、结算、提现和导出再以服务端会话中的 `merchant_id` 强制限定。如未来要改成多客户共库 SaaS，必须另立数据模型和迁移项目，不能只向 MyBatis 拦截器的表名清单里追加名称。

## 2. 已实现的 P0 闭环

### 2.1 商户状态拆分

| 维度 | 状态 | 作用 |
| --- | --- | --- |
| 账号 | ENABLED / DISABLED | 是否允许登录商户工作台 |
| 经营 | ACTIVE / SUSPENDED / CLOSED | 是否允许新销售和商品经营 |
| 履约 | ENABLED / PLATFORM_ONLY / DISABLED | 历史订单由商户处理、平台接管或暂停处理 |
| 提现 | ENABLED / FROZEN | 是否允许发起新提现 |
| 结算 | ENABLED / FROZEN | 到期货款是否从待结算释放到可提现 |
| 保证金 | NORMAL / FROZEN | 保证金风险状态 |
| 审核 | PENDING / APPROVED / REJECTED | 平台准入审核结果 |
| 退出 | NORMAL / EXITING / EXITED | 正常经营、清退处理和完成退出 |

“全面冻结”采用安全预设：暂停新销售、冻结提现、冻结新货款释放，但保留账号登录和历史订单/售后履约。只有明确禁用账号时才禁止登录。

### 2.2 后端数据隔离

商户身份来自后台登录会话，前端传入的 merchantId 不能扩大查询范围。隔离已覆盖：

- 商户资料；
- 商品与 SKU；
- 发货和退货地址；
- 订单列表、订单详情、订单工作统计、发货和客服备注；
- 售后列表、售后审核和退货收货；
- 货款账户、结算明细、资金总账、保证金流水、提现及审批轨迹。

平台账号的 merchantId 为空，按租户范围管理；商户账号只按会话中的 merchantId 查询。导出接口必须复用同一查询条件，禁止另写无商户条件的导出 SQL。

### 2.3 商品审核与快照

商户商品必须明确归属 merchant_id。商户修改销售价或结算价前必须下架，保存后回到待审核流程；平台批准的版本才可重新上架。订单项保存成交时的商户、结算价、结算周期、奖金模式和商品信息快照，后续商品改价不影响历史订单。

### 2.4 商户资金总账

资金账户保存当前余额，资金总账保存每次变化及变化后的余额。总账覆盖：

- 订单进入待结算；
- 售后窗口和结算等待期结束后释放可提现；
- 售后退款冲回；
- 申请提现冻结余额；
- 提现驳回解冻并优先抵扣欠款；
- 财务确认打款；
- 保证金转入、线下收款和释放。

财务可以从第一笔流水复算待结算、可提现、提现冻结、保证金、欠款和累计打款，而不是只依赖一组余额字段。

### 2.5 提现与保证金

当前有效提现流程为：提交申请 → 财务/发票审核 → 待收发票或待打款 → 付款处理中 → 已打款 → 已完成。付款失败可保留冻结资金后重新付款或驳回，商户在财务处理前可撤回，平台可风控冻结并恢复到冻结前状态；驳回或撤回只允许释放一次冻结金额。每次状态变化保存审批轨迹，申请时保存商户主体和银行卡资料快照，历史记录不会随商户后来修改银行卡而变化。

保证金包含应缴、已缴、缺口和风险状态。保证金不足时禁止提交商品审核和申请提现；退款损失按“可提现 → 保证金 → 欠款”处理。商户退出前必须执行退出检查；存在上架商品、未完成订单、开放售后、待结算货款、处理中提现或任何非零资金余额时，后端拒绝确认退出。完成停止经营、历史履约、售后处理、清偿欠款、保证金释放和财务归档后，才允许关闭账号并确认退出，不允许直接删除商户。

每个新商户账户从零余额期初流水开始。后台“账本对账”逐项比较账户当前余额和末笔总账余额，覆盖待结算、可提现、提现冻结、保证金、欠款和累计打款；任何差异都必须先查明原因，禁止仅修改页面数字掩盖账务断点。

## 3. 业务不变量

以下条件必须由后端和数据库共同保证：

1. 商户账号不能通过传参查询或操作其他商户数据。
2. 经营暂停后，未支付订单不能继续付款，但已支付订单仍能按履约状态处理。
3. 商户结算价和结算周期以订单快照为准。
4. 同一订单项只能生成一笔商户结算记录。
5. 同一提现 requestNo 只能冻结一次余额。
6. 已驳回或已打款的提现不能再次解冻或付款。
7. 账户余额每次变化必须产生同事务资金流水。
8. 结算释放时间不得早于售后入口截止时间和商品结算等待时间。
9. 商户商品产生团队奖金时，只能进入明确的复购/报单业务区，不能混入普通公开商城。

## 4. 已实现的父交易 + 商户子订单

跨商户购物车已采用以下模型；历史订单和单商户订单继续沿用原结构，不需要转换：

- 新增交易父单 `dms_shop_trade`：记录用户的一次结算、一次支付请求和支付总金额。
- 现有商城订单升级为商户子单：每张子单只属于一个商户，独立运费、履约、售后和结算。
- 支付回调：校验主单金额后，在同一事务中把全部子单从待支付改为已支付。
- 退款：按子单和订单项独立申请，支付宝退款使用原父交易支付单号和每笔唯一退款请求号；累计可退金额继续由子单财务账约束，不能超过各子单实付。
- 前端：用户只提交和支付一次；订单列表分别展示各商户子单，并标注共同的联合支付单号。
- 商户后台：永远只看到自己的子单；平台后台可从主单查看所有子单。

平台订单页可从任一子单打开联合支付详情，核对父交易状态、支付方式、子单金额合计、已完成退款和全部履约子单。该汇总接口拒绝商户会话，避免商户借父交易读取同一次付款中的其他商户订单。商户在履约状态为 `ENABLED` 时可对自己的子单进行单笔/批量发货及处理正常售后；平台接管或冻结履约后，页面同步隐藏操作入口，服务端仍会再次拒绝直接调用。平台取消和人工退款属于跨资金异常操作，不下放给商户。

待付款阶段取消任一子单会关闭整笔父交易并释放全部子单库存；支付前先完整校验所有子单，再在同一事务入账。已付款后各子单独立发货、确认收货、售后、退款、商户货款与团队奖金，不允许一个商户操作另一个商户的子单。

## 5. 后续优先级

### P1：进入真实多商户联调前

1. 在接入真实支付渠道账单后，把当前账户与资金总账对账扩展为“账户、内部总账、支付渠道、退款渠道”日终四方对账。
2. 客户确认优惠券、满减和平台补贴规则后，增加父交易优惠分摊快照；当前基座尚未启用跨商户平台优惠。

已完成：付款处理中、付款失败、商户撤回、风控冻结/恢复及提现归档；账户与末笔总账余额对账；商户退出硬检查与阻断。它们不再属于待开发项，但仍需客户环境中的财务人员按实际银行流程验收。

### P2：规模运营优化

1. 商户 SLA、发货超时和保证金缺口预警。已实现退货审核通过后客户超时未寄回的可配置自动关闭，默认7天，设为0可禁用。
2. 商户分级风控规则和高风险商品独立保证金/结算周期。
3. 大批量订单、结算和总账导出改为异步任务，并保持下载文件的商户范围隔离。
4. 财务凭证改为受控上传与权限下载，不直接保存公开 URL。

## 6. 验收重点

验收至少覆盖两个商户和一个平台账号，使用相同关键词、相同订单状态、手工篡改 merchantId 以及在批量发货表中填写其他商户订单号的方式验证隔离；再覆盖暂停经营后旧订单可发货、履约切换平台接管后商户不能发货或处理售后、未支付订单不可支付、结算不释放、提现不可申请。资金测试必须逐笔核对账户余额、总账变化和审批事件三者一致。
