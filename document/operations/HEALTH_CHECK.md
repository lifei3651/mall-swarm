# 服务健康检查与告警说明

## 1. 当前健康检查入口

生产环境已经启用 Spring Boot Actuator 健康检查：

```text
http://127.0.0.1:8086/actuator/health
```

该地址只允许在服务器本机访问。公网地址 `/api/actuator/**` 由 Nginx 固定返回 404，禁止直接暴露数据库、Redis 或第三方服务信息。

服务器本机检查示例：

```bash
curl --fail --silent http://127.0.0.1:8086/actuator/health
```

正常响应：

```json
{"status":"UP"}
```

非 `UP`、连接失败或请求超时均应视为异常并触发告警。

## 2. 各依赖的检查口径

| 检查项 | 自动健康检查 | 判断口径 | 说明 |
| --- | --- | --- | --- |
| 应用进程 | 是 | Actuator 返回 `UP` | 无法连接或超时表示应用不可用 |
| MySQL 数据库 | 是 | 数据源健康指示器纳入总状态 | 连接失败时总状态不会是 `UP` |
| Redis | 是 | Redis 健康指示器纳入总状态 | 连接失败时总状态不会是 `UP` |
| 支付宝 | 配置就绪检查 | 应用 ID、应用私钥、支付宝公钥、网关和回调地址均已配置 | 健康检查禁止创建真实支付；正式可用性通过小额支付、异步回调和订单状态联调确认 |
| 短信服务 | 配置就绪检查 | 服务开关、访问凭证、签名及各业务模板均已配置 | 健康检查禁止发送真实短信；正式可用性通过指定测试手机号和各业务模板联调确认 |

生产配置使用 `show-details: never`，因此健康响应只返回汇总状态，不在接口中泄露组件名称、连接地址、账号或错误堆栈。数据库、Redis 的具体故障原因应结合服务日志和各自的运维命令排查。

## 3. 支付宝与短信为什么不做主动网络探活

支付宝支付接口需要业务订单、金额、签名和回调闭环；短信接口会产生真实发送记录和费用。定时调用这类接口作为健康检查会制造测试订单、重复短信或额外费用，也可能触发平台风控。

因此分为两层：

1. 日常监控只检查应用、数据库、Redis 和第三方配置是否齐全。
2. 新客户部署、密钥更换、模板变更或正式发布前，再执行一次受控的真实联调。

真实联调必须使用专门测试订单或测试手机号，并核对：

- 支付宝：创建支付成功、用户付款成功、异步通知验签成功、订单状态更新且重复回调不重复入账。
- 短信：注册、登录、找回密码、转账、提现、支付和支付密码模板按客户实际启用范围逐项验证。

## 4. 建议监控规则

| 监控项 | 建议频率 | 超时 | 告警条件 |
| --- | --- | --- | --- |
| `/actuator/health` | 30 秒 | 5 秒 | 连续 3 次非 `UP`、超时或无法连接 |
| HTTPS 商城首页 | 60 秒 | 10 秒 | 连续 3 次非 2xx 或核心资源加载失败 |
| HTTPS 管理后台 | 60 秒 | 10 秒 | 连续 3 次非 2xx 或核心资源加载失败 |

恢复后应自动发送恢复通知，避免运维人员只收到故障通知而不知道服务已经恢复。

## 5. 故障处理顺序

1. 在服务器本机检查 `/actuator/health`。
2. 检查 Java 服务、Nginx、MySQL、Redis 的运行状态。
3. 查看发布后日志中最早出现的异常，不只看最后一条错误。
4. 若仅支付宝或短信业务异常，检查对应平台状态、服务器出口网络、白名单和配置就绪情况。
5. 不得为了恢复健康状态而删除订单、会员、财务或奖金数据。
