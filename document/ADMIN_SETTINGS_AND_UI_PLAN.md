# 后台设置中心与统一 UI 规划

日期：2026-09-13。状态：设计提案，待选定视觉方案后实施。基线：cea8b490 / 1.0.139。

本次不改变真实资金规则、不启用提现渠道、不发布服务器或小程序。线上后台只读版本为 1.0.139 / e6a11c3d。本方案不是功能上线回执。

## 一、结论

保留一个「商城设置」入口，将经营规则按业务分组集中；日常操作仍留在商品、订单、会员、营销和财务。统一的是栅格、字号、行高、对齐、操作位置和反馈方式，不是仅仅换颜色，也不是把手机界面放大到电脑。

余额提现不再以推广资格作为唯一入口条件。拟改为：有效可提现余额 + 账户安全验证 + 后台提现规则。拥有余额不自动授予推广资格。此项需要服务端账户与账本改造，不能只去掉前端提示。

## 三、主导航重新归类

| 主入口 | 日常工作 |
| --- | --- |
| 工作台 | 待办、经营概览，状态来自实际数据，不能用固定文字冒充健康检查 |
| 商品 | 商品、分类规格、库存、商家商品审核、服务地址 |
| 订单 | 订单、售后、评价、客服工单 |
| 会员 | 会员资料、团队、业绩与关系调整 |
| 营销 | 优惠券、秒杀、直播、消息运营 |
| 财务 | 余额账户/流水、奖金、提现审核/打款/记录、商家结算 |
| 商城设置 | 全部经营配置的统一索引及分组编辑 |
| 系统与审计 | 后台账号权限、操作日志、风控、数据迁移 |

旧路由保留或兼容重定向；权限沿用并由服务端检查，不因入口合并扩大权限。商家只看到其授权设置与数据，不出现平台余额规则。营销入口归类不等于授权商家发行平台优惠券。

## 四、设置中心分组

入口提供设置搜索（支持「余额、人工加款、银行卡、客服」等别名），搜索结果标明所属分类；页面只渲染当前账号有权查看的结果。高频项目可固定显示，但不重复维护两份配置。

| 分类 | 设置内容 | 当前落点 / 实施界限 |
| --- | --- | --- |
| 基础资料 | 主体、资质、备案、协议 | 现有 `/tenant/profile`、协议页面；保留原有公开信息规则 |
| 外观与页面 | 品牌主题、首页/分类/详情版型 | 现有 `/tenant/list`；前后台共用品牌值，后台仍有专属桌面排版 |
| 交易规则 | 订单、配送、售后相关可配置项 | 梳理已有字段后接入；无字段的明确「待接入」，不伪造开关 |
| 余额与提现 | 来源资格、审核、打款、渠道、额度 | 新配置模型；现有会员入口仍与推广绑定，待服务端改造 |
| 营销规则 | 优惠券承担及奖金口径、秒杀/复购基础规则 | 券的具体适用商品和发行条款仍在券编辑页，不做全局覆盖已发行条款 |
| 会员与团队 | 推广开通、查看权限、奖金规则入口 | 现有 `/tenant/business-modes`、`/audit/settings`、`/tenant/bonus-config` |
| 客服与消息 | 联系方式、工作时间、已支持的客服通道设置 | 现有资料及消息运营；内置工单、小程序原生客服和外部微信客服分清名称 |
| 服务接入 | 支付、短信、实名、ERP等接入状态与指引 | 技术部署配置只显示状态与维护入口；不把密钥搬进普通设置页，不把「未接入」显示成可启用 |

设置总览只显示分类名称、简短摘要、异常项数量及入口，不做满屏彩色卡片。操作日志可从各设置页查看，不能以集中入口取消原有审计记录。

## 五、余额与提现设置详案

### 1. 配置分层

| 项目 | 推荐交互与含义 |
| --- | --- |
| 提现服务 | 总开关，仅影响新申请；关闭时必须填写给会员看的原因，保留记录查询及在途处理 |
| 可提现余额来源 | 按业务收入、人工增加余额等实际账本来源配置；未识别来源单独处理，不自动推断 |
| 人工增加余额 | 「允许提现」开关；人工加款时显示实际适用规则及用途；记录来源与规则版本 |
| 审核方式 | 人工审核 / 按已配置的风险规则自动审核；不能把自动审核解释为自动到账 |
| 打款方式 | 接口打款 / 财务线下转账；仅展示该渠道确已接入的方式 |
| 提现渠道 | 微信、支付宝按接入状态；银行卡为待实现的线下转账目标，不宣称已支持银行卡自动转账 |
| 限额 | 最低金额、单笔/每日上限、频次及已支持的费用规则；未实现字段不能只是前端输入框 |
| 必要验证 | 实名、支付密码、账户异常限制按安全规则执行，不提供随意绕过验证的开关 |

默认保持当前运行规则，不能因页面更新默认开启任何选项。新能力未上线时明确标识「待接入」，禁用控件旁解释原因。

### 2. 人工余额与历史余额

- 总余额、可提现余额、不可提现余额、在途提现分别展示。不能提现部分仍能否消费由既有消费规则决定，不隐式改变。
- 来源需要贯穿入账、消费扣款、退款恢复与提现退回。退款应恢复原来源组成，防止不可提现额度经退款变可提现。
- 变更默认作用于规则生效后的新入账；历史余额单列「历史余额处理」，先核对来源并预览影响人数与金额，再由有权限的人明确执行。不能改一个布尔值便追溯重写所有账。
- 全部历史余额允许提现是可支持的业务选择，但必须有明确范围、基准时点、账本快照与审计；冻结/争议/已提现部分不能重复放开。
- 不因为“有余额”自动给推广资格，也不因为关闭推广资格抹掉已合法形成的提现权益。

### 3. 人工打款闭环

申请 → 待审核 → 待打款 → 财务线下转账 → 后台登记打款凭证 → 已打款。

- 拒绝必须填原因并按原账本规则退回；当前系统申请已扣余额，标记已打款不得再次扣减。
- 登记包括打款金额、时间、收款目标、银行流水/凭证、备注、操作人与复核人；金额与申请匹配。打款凭证不在普通列表公开。
- 分开“审核”“登记打款”“复核”“配置规则”权限；重复点击与并发请求保证幂等。
- 官方通道处理中或结果未知时不能直接改成线下已打款，必须先查证避免重复出款。
- 不可用“编辑提现状态”的普通下拉框代替受校验的状态转换。

### 4. 银行卡支持边界

会员端拟新增本人收款银行卡维护及提现选择；服务端校验收款姓名、加密保存必要信息、列表脱敏、权限校验、操作审计。首期优先支持人工审核 + 线下银行卡转账。银行卡接口自动打款是独立接入，不因出现银行列或开关就算完成。

### 5. 保存与生效

资金规则显式保存，不开关即自动生效。保存前仅一次影响确认，展示变更前后、适用范围、生效时间、在途处理方式，并填写原因。保留版本和操作日志，旧版本并发保存应提示冲突，不覆盖他人修改。回退也是新版本；已发券、已申请提现和已生成结算快照不能被回退追溯篡改。

## 六、统一后台 UI 规范

- 白底、浅灰分组背景、细分隔线。主色复用品牌配置；设计稿以现有后台 #5669e8 示意，不把绿色当作用户批准的新品牌。
- 基础间距 8px；页边距 24px、组内 16/24px。正文 14–16px、页面标题 22px、分组标题 16px；辅助文案不靠极浅灰缩小字号。
- 左导航约 200–220px，设置分类约 170px；窄窗口折叠分类导航。主区域 min-width:0，不让表单撑出页面。
- 设置项统一整行：名称及一句解释在左，开关/选项在右；复杂项进入详情或展开。上下行同一左右边界，不插入居中短按钮块。
- 表单标签同宽、输入框同高，行高按内容 56/72px；开关有文字状态，选项有明确展开箭头；取消和保存位置统一。
- 普通字段不反复弹窗；失败在对应字段/页内说明，需注意的阻断错误再弹窗。资金、删除、权限改变才做必要确认。
- 列表统一「标题与主操作 → 筛选 → 表格 → 分页」；金额右对齐及等宽数字；主要标识固定，次要资料放详情侧栏。确实宽的数据表允许局部横向滚动，不整页横向滚动、不藏掉关键列。
- 详情统一侧栏；较长编辑用独立页面。弹窗只处理短且明确的任务，不套多层弹窗。
- 组件至少包含正常、加载、空、失败、禁用、长文本、无权限及窄窗口状态。焦点可见、键盘可操作、状态不只靠颜色。

## 七、实施顺序与验收

1. 选定桌面布局方案。图为结构与视觉参考，所有规则均以本文及后续确认的字段为准。
2. 实现后台公共布局与页面组件；先统一已有资料设置、业务模式、提现列表，不改金融含义。
3. 建设置中心索引与权限映射，迁移既有配置入口；按字段保存，避免旧整租户对象覆盖无关配置。
4. 单独实现余额来源、非推广账户提现、人工打款、银行卡收款及迁移。先隔离数据库与假数据验证，再受控发布，保持所有新规则默认不启用。
5. 覆盖后台各菜单及各角色逐页验收，记录未覆盖项。桌面 1440/1280/1024、表格溢出、长名称、保存失败/重试/并发、权限绕过、重复打款、驳回退回、退款来源、历史余额迁移幂等都是验收项。

本次只完成设置架构、规则边界和设计提案，不标记后台改造或资金闭环已完成。
