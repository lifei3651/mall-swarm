# 1.0.164 售后退货地址补配阻断修复：本机验证记录

## 问题与根因

用户反馈：实体退货/换货申请在管理后台审核时提示“请先为该订单商品配置可用退货地址，再通过售后”；随后给商品补配退货地址，旧申请审核仍提示相同错误，退款流程无法继续。

源码核对：申请创建时仅把当时解析出的地址写入售后单快照；未配置时允许创建空快照。审核只检查该快照，不重新读取商品。商品后来补配地址不会改变旧售后单，因此持续阻断。新商品创建、商品管理表单和重新上架原先也未统一要求可用退货地址。

## 修复边界

- 仅待审核、审核通过的实体退货/换货申请，在历史快照为空时按该订单商品当前配置或所属商户默认退货地址重新解析，租户、商户、地址类型与启用状态均须匹配；混用不同仓库仍拒绝。与审核状态一同持久化；已有非空快照不覆盖。
- 新商品创建/发布时后端要求有效退货地址；商品后台仅列有效地址并在保存前校验。旧商品从下架重新上架也须补齐；旧在售商品不因本次代码更改被自动下架，尚需正式库只读扫描。
- 审核通过退货退款只进入“待寄回”；**不是立即原路退款**。顾客寄回、后台确认收货后才进入后续退款/账务链路；换货不进入退款链路。
- 无数据库迁移或批量修改。禁止直接改写历史售后地址快照、订单金额或退款账本。

## 本机验证与同类扫描

- 新增服务层回归：旧申请空地址→审核拒绝→补配地址→再次审核成功、地址持久化；将其他租户地址挂在商品上仍拒绝；新商品无地址不能发布、配置有效地址后可发布。
- 审核 `updateAuditScoped` 所有状态迁移共用同一 SQL；只在原快照为空时写入解析结果，拒绝/关闭和历史非空快照均不被改写。搜索申请、人工退款、商品创建/更新/发布/上架和后台地址选择入口，已覆盖同一缺口。
- `ShopFreightServiceTest` 37 项通过；后端全套 `./mvnw -pl mall-distribution -am test -q` 790 项通过、0 失败/错误；管理后台 `npm test` 218 项通过、生产构建通过；小程序 `npm run check` 通过。本机模拟数据不是正式库证据，完整跨端候选 C/T 仍须在冻结提交后重跑。

## 关闭条件

取得订单号或售后单号后，只读核对：订单租户/商户、售后类型与状态、原地址快照、订单商品当前 `return_address_id`、地址启用及归属；按租户/商户扫描同类“待审核实体退货空快照”和“在售商品无有效退货地址”。新候选完成独立封包/留档及授权的 S/W 后，再用原单或受控测试单完成审核、退货寄回、确认收货、渠道退款回执及订单/奖金/资金对账和真机 R。未取得上述证据时 P0-13 不关闭。
